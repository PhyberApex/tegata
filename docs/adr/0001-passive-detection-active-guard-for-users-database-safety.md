# Out-of-Band Edit detection stays passive; the Enabled-Count Guard actively blocks

Two safety mechanisms protect the Authelia Users Database, and they respond to their trigger differently on purpose. Out-of-Band Edit detection (a Baseline Hash compared on every `readDatabase()`) only ever surfaces a banner — it never blocks a Tegata operation, because the edit it's reporting already happened; refusing to operate would just add a second failure (an admin locked out of the identity system) on top of whatever caused the first one, and the out-of-band edit might itself have been a legitimate emergency repair. The Enabled-Count Guard, by contrast, actively rejects the write (pending a `confirm: true` retry) when `deleteUser` or a disabling `updateUser` would drop the enabled-user count to 0 or 1 — because that write hasn't happened yet, and this is the one case where stopping it costs nothing but an extra click.

The general rule: if the risky state already exists, report it; if the write is about to create it, block it.

An Unreadable Users Database (CONTEXT.md) is a third application of that same rule, not a change to either mechanism above. The unreadable read has already happened by the time a write is attempted, so — like an Out-of-Band Edit — it's reported: the database-integrity status endpoint and the admin banner surface it, with a reason. But the overwrite an unreadable read would otherwise lead to (a write path replacing the real file with an empty map, since it can't see the existing users) hasn't happened yet, so — like the Enabled-Count Guard — it's blocked, with every write refused as a 503 until a readable file is back. Out-of-Band Edit detection itself keeps never blocking; a database that's unreadable is a different state from one that's merely out of sync with its Baseline Hash, detected and handled separately.
